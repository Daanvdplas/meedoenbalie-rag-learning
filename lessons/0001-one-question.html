The connection

The search tool is exposed through MCP: the connection Codex uses to call Rust search and get results back.

Codex chooses the search text. Rust performs the search.

Rust finds passages with related meaning.

A local model turns the search text into numbers, called an embedding. Rust compares it with the document sections and returns the highest-ranked passages, with source IDs and dates.

Codex writes. Rust checks the citations.

Codex returns an answer, citations, and unknowns. Rust checks that each citation belongs to a returned section with the right source date and an exact quote. The browser then shows the answer and actual searches.

Where certainty ends

Two places on 1 September does not establish availability today. The intended answer keeps current places unknown.

A valid quote does not prove that every sentence in the answer is true. These checks cannot establish that the model interpreted the source correctly.

Step 1 of 4

How do the documents become searchable?
5 fictional documents→30 sections→Local MiniLM embeddings→Index in memory

The title, section heading, and exact text become each section's embedding input. The web app and the search subprocess load separate indexes. They use the same Rust retrieval implementation.

src/lib.rs:100 · src/main.rs:21. A high similarity score means related text; it is not a confidence score for the answer.

Why separate search from answer writing?

Search returns evidence. Codex turns that evidence into language. This separation lets you inspect the actual passages and evaluate retrieval separately from the answer.

The trade-off: the writer can miss a needed passage or misinterpret one. More searches can help, but the four-search limit does not guarantee a complete answer.

Other code lives beside this path: the CLI calls the same search, and experiment compares retrieval approaches and separately grades saved answers. That evaluation workflow is outside the demo screen.
