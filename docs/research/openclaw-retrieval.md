# What OpenClaw can teach our SQLite retrieval experiments

Research date: **2 November 2026**. Research only: no implementation, benchmark, model call or demonstrated quality/speed improvement. A fresh source investigator and an independent reviewer examined the official project. This complements the [three-mode investigation (draft PR #64)](https://github.com/Daanvdplas/meedoenbalie-rag-learning/pull/64) and [activity-retrieval investigation (draft PR #65)](https://github.com/Daanvdplas/meedoenbalie-rag-learning/pull/65).

## Recommendation for this project

**Borrow the separation between source data, a persistent index, candidate retrieval and result selection. Keep every intervention independently selectable.** SQLite is the requested database option; no PostgreSQL migration or adoption of the OpenClaw framework is proposed.

Our current corpus is five fictional activities / thirty sections. It already has local MiniLM vectors, exact cosine search and an experiment-only BM25 baseline. [`Index::load`](../../src/lib.rs) embeds the document inputs at startup; `.model-cache` caches model files, not these document vectors. Moving unchanged data into SQLite does not by itself improve relevance.

The first useful additions are a rebuildable SQLite index with correctly invalidated embedding reuse, larger internal candidate pools separated from the final context budget, and explicit retrieval-mode/fallback reporting. Optional diversity selection is a later controlled experiment. Keep activity expansion and source-verified structured filtering as separate interventions; an assistant's personal-memory ranking rules do not establish suitability for activities.

## A more capable but detachable Rust design

The following is our proposed design, not existing code or a claim that OpenClaw exposes these exact interchangeable interfaces.

| Independent choice | Proposed variants |
| --- | --- |
| Source representation | Existing canonical sections; later bounded activity views and source-backed typed fields |
| Storage adapter | Existing document/in-memory route; SQLite with versioned schema and rebuildable indexes |
| Candidate retrieval | Existing exact vector scorer; existing BM25; optional SQLite FTS5 as a distinct lexical implementation; hybrid |
| Fusion and selection | Explicitly versioned RRF or an independently specified weighted strategy; deterministic ties and deduplication; optional MMR |
| Context assembly | Selected unchanged sections; separately bounded same-activity expansion |

SQLite must be removable as an adapter: loading the documents and using the original route should remain possible without a database or extension. SQLite storage does not mandate FTS5, and hybrid does not mandate a particular storage engine. Preserve stable `(document ID, section ID)` identities, exact text and source dates across adapters. Do not send expected answers or evaluation labels into any index.

Source validity differs from memory recency. OpenClaw's decay/importance/project rules serve personal memory. An older verified activity schedule can remain correct; a newer note can be incomplete. Keep effective dates, last verification, unknown capacity and supersession explicit rather than automatically halving activity relevance every thirty days. Our filters must distinguish requirements from preferences and unknown from false. No resident-profile storage is introduced.

Keep embedding and retrieval work local as in the current prototype; SQLite alone is not a privacy boundary. Codex still receives the question and selected text for answer generation. OpenClaw supports multiple embedding providers, so its use of SQLite is not evidence that all of its processing is local. Preserve our stronger source-plus-date citation requirements rather than replacing them with file/line references.

## Experiments that can explain a difference

1. **Storage and cache only:** same source snapshot, stored vectors, scorer, precision, tie policy and query; compare in-memory/document versus SQLite reads. Check ordered identities and numeric tolerances, and measure cold build, warm startup/query, incremental updates, deletions and rebuilds separately. Switching to FTS5 at this point would confound storage with ranking. A cache experiment should show avoided embedding work; it does not establish better relevance.
2. **Search and fusion:** keep corpus, storage, representation and final passage/token budgets fixed; compare vector, existing BM25 and hybrid. Treat FTS5's BM25/tokenizer/query behavior as a new retriever version, not identical to our current Rust BM25. Declare candidate depth, normalization, fusion parameters and zero-match behavior before the run. Candidate-set size and lexical expansion affect results and cost even with the same final top-k.
3. **Diversity only:** compare the same hybrid candidates with MMR off/on, preserving the final budget and all other settings. Score missing AND-combinations of evidence and relevant activities wrongly omitted, alongside duplicates. Distinct activities are not intrinsically better than the two sections needed to support one answer.
4. **Representation and filters separately:** use the activity-expansion and typed-filter protocols from draft PR #65. Count added context, source annotation and query-parsing work. A supplied correct typed filter is not proof of reliable natural-language parsing.
5. **Whole-agent follow-up:** after local retrieval-only comparisons, use the same Codex prompt/model/tool limit for a predeclared balanced subset. Record first-search and final evidence, calls, internal branch searches, context, time and failures. A full eighteen-question × three-agent run exceeds the historical forty-generation protocol; use an appropriately authorized new protocol or smaller balanced plan. Keep the free-text AI judge paused.

Start with one controlled question and then the existing eighteen regression questions; these are already seen, not a new holdout. Preserve N/A for incomplete relevance labels and source-free unknown questions. Evidence coverage and valid citations are not free-answer correctness or a calibrated confidence score. Record the actual executed mode and any declared fallback; never pool degraded keyword results into the vector arm without identifying them. Existing artifacts remain readable and unchanged.

A future HTML comparison should show a question and its expected evidence, selected settings, found/missing facts, actual passages, branch contributions, and cold/warm work. Show wins, losses and failures. Results should explain whether a difference came from storage, candidate retrieval, result selection or context assembly. No page, command or new experiment result is added by this note.

## First slice and deferred work

The useful first slice is the shared retrieval boundary, detachable SQLite persistence/cache, truthful local retrieval-only records and an inspectable three-mode comparison. Then evaluate bounded activity expansion and exact fields. Larger candidate pools and MMR are optional ablations; a weighted hybrid is a separate challenger to RRF, not a prerequisite. Avoid adding memory decay, write-time importance, autonomous memory ingestion, graph memory or a learned reranker before a measured failure warrants them.
